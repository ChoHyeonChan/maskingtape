# bench 동작 원리 — 발표 Q&A용

발표평가에서 "이 코드가 어떻게 도는가", "왜 이렇게 만들었는가"를 답하려고 정리한 문서다([#459](https://github.com/ChoHyeonChan/maskingtape/issues/459)).
항목마다 **한 줄 → 동작 → 이렇게 만든 이유 → 다른 방법을 안 쓴 이유 → 예상 질문 → 코드** 순서로 적는다.
숫자는 [bench/README.md](../README.md) 「머지 마감 뒤 재측정」(main `2802949`, 2026-10-26)의 값이다. 이 문서에서 새로 잰 숫자는 없다.

## 1. 합성 데이터 생성기

**한 줄.** 문장 틀에 가짜 개인정보를 끼워 넣으면서 그 값이 들어간 위치(start, end)를 정답으로 같이 적는다.

**동작.**
1. `entities.py`가 종류별로 가짜 값을 만든다. 주민번호·카드·사업자번호는 검증 숫자까지 맞춘다.
2. `documents.py`가 `"고객 {name}님 {phone}로 발송"` 같은 틀의 `{종류}` 자리를 차례로 바꾼다.
   바꾸기 직전까지 이어 붙인 글의 길이가 그 값의 시작 위치다.
3. 전체 문서의 25%는 개인정보가 없는 문서다. 주문번호·송장번호처럼 숫자만 닮은 값(`distractors.py`)이 들어 있어
   오탐을 잰다.
4. 시드를 고정해서 같은 명령이면 바이트까지 같은 파일이 나온다(`--count 500 --seed 42` → `synth_v1.jsonl`).
   테스트가 저장소의 파일과 다시 만든 파일을 비교한다.

**이렇게 만든 이유.** 실제 개인정보는 저장소에 넣을 수 없다(대회 규정, 개인정보 보호 도구가 개인정보를 유출하면 안 된다).
외부 데이터셋은 재배포 제한이 있다. 합성 데이터는 누구나 같은 파일을 다시 만들어 숫자를 확인할 수 있다.

**다른 방법을 안 쓴 이유.**
- 사람이 문서를 모아 손으로 라벨을 다는 방식: 진짜 개인정보가 섞일 위험이 있고 재현이 안 된다.
- LLM에게 문서를 쓰게 하는 방식: 같은 결과가 다시 나온다는 보장이 없고, 정답 위치를 따로 맞춰야 한다.

**예상 질문.**
- *합성 데이터 점수를 믿을 수 있나?* → 그대로는 못 믿는다. 그래서 4·5번 항목처럼 상한으로 읽고, 규칙 조정에 안 쓴
  보고용 세트와 외부 데이터로 따로 잰다.
- *이름은 어떻게 만드나?* → 흔한 성 30개와 이름 음절 32개를 조합한다. 세 글자 위주이고 두 글자를 15% 섞는다(문서 성격별 세트).

**코드.** [`generator/entities.py`](../generator/entities.py) · [`generator/documents.py`](../generator/documents.py) ·
[`generator/distractors.py`](../generator/distractors.py) · [`generate_dataset.py`](../generate_dataset.py)

## 2. 채점 — 완전 일치 precision · recall · F1 · F2

**한 줄.** 정답과 탐지를 `(종류, 시작, 끝)` 세 값이 모두 같을 때만 맞힌 것으로 센다.

**동작.**
1. 정답 라벨과 core `Pipeline.scan()`의 결과를 각각 `(kind, start, end)` 집합으로 만든다.
2. 교집합이 tp(맞힘), 탐지에만 있으면 fp(오탐), 정답에만 있으면 fn(미탐)이다.
3. precision = tp / (tp + fp), recall = tp / (tp + fn),
   Fβ = (1 + β²) · P · R / (β² · P + R). F1은 β = 1, F2는 β = 2다.
4. 종류별로 따로 세고, 전체는 모든 종류의 tp·fp·fn을 더해서 계산한다(micro).

**이렇게 만든 이유.**
- **F2를 대표로 보는 이유:** 개인정보는 놓치면(미탐) 그대로 새고, 더 가리면(오탐) 읽기 불편할 뿐이다. F2는 recall을
  precision보다 4배 무겁게 본다(β² = 4). PII 평가에서 쓰는 관행이다(Presidio 평가 도구도 β = 2를 권한다).
- **완전 일치를 쓰는 이유:** 가장 엄격한 기준이라 점수를 부풀리지 않는다. 한 글자라도 경계가 다르면 미탐 1 + 오탐 1로 센다.

**다른 방법을 안 쓴 이유.**
- 겹치기만 하면 맞힌 것으로 치는 기준(overlap): 너무 넓게 가려도 맞힌 것이 된다. 외부 도구 비교처럼 도구마다 경계를
  자르는 관행이 다를 때만 쓴다(7번).
- 문서 단위 채점(문서에 개인정보가 있다/없다): 어느 값을 놓쳤는지 알 수 없다.

**예상 질문.**
- *완전 일치면 "김민수님"에서 "님"까지 가린 것도 틀린 건가?* → 그렇다. 그래서 3번의 유출 기준 재현율을 같이 본다.
- *F1과 F2가 다르게 말하면?* → 하이브리드는 오탐이 늘어 F1이 덜 오르지만 F2는 크게 오른다. KDPII 이름에서 규칙 전용
  F1 0.457 · F2 0.347, 하이브리드 F1 0.593 · F2 0.711이다.

**코드.** [`evaluators/evaluate.py`](../evaluators/evaluate.py) — `gold_spans`, `predicted_spans`, `Counts.fbeta`

## 3. 미탐·오탐 분해 — 그 미탐은 유출인가

**한 줄.** 완전 일치에서 틀린 것을 "실제로 새는가" 기준으로 다시 나눈다.

**동작.**
- 미탐은 정답 글자가 탐지로 얼마나 덮였는지로 나눈다. **가려짐**(다 덮임, 경계만 다름)·**부분 유출**(일부만 덮임)·
  **완전 유출**(겹치는 탐지 없음).
- 오탐은 **경계 불일치**(어떤 정답과 겹침)와 **엉뚱한 곳**(어떤 정답과도 안 겹침)으로 나눈다.
- 유출 기준 재현율 = (맞힘 + 가려짐) / 정답 수.

**이렇게 만든 이유.** 완전 일치는 엄격하지만 "샌다"와 "한 글자 더 가렸다"를 구분하지 못한다. 합성 500건의 이름 오탐
12건은 모두 경계 차이다(두 글자 이름 뒤 조사까지 가림). 이름은 다 가려지므로 유출은 아니다. 둘을 나눠야 고칠 순서를 정할 수 있다.

**다른 방법을 안 쓴 이유.** 처음부터 overlap으로만 채점하면 경계 오류가 아예 안 보인다. 완전 일치를 기본으로 두고
유출 기준을 덧붙여야 둘 다 보인다.

**예상 질문.** *유출 기준 숫자만 쓰면 더 좋아 보이지 않나?* → 그래서 대표 숫자는 완전 일치로 쓰고, 유출 기준은 "새는가"를
설명할 때만 쓴다.

**코드.** [`evaluators/error_breakdown.py`](../evaluators/error_breakdown.py)

## 4. 벤치 숫자를 실제 성능의 상한으로 읽어야 하는 이유

**한 줄.** 생성기·규칙·모델이 같은 데이터를 보고 만들어져서, 합성 세트 점수는 처음 보는 문서보다 높게 나온다.

**근거 넷.**
1. **생성기가 core의 형식을 그대로 따른다.** `entities.py`는 core의 전화 정규식(`_LANDLINE_RE`)과 카드 검증(`_luhn_ok`)을
   직접 가져오고, 주민번호 가중치는 core와 같은 규칙으로 다시 썼다. 그래서 구조화 10종의 1.000은 "core가 아는 형식을
   경계까지 정확히 잡는가"를 본 값이지, 처음 보는 표기까지 다 잡는다는 뜻이 아니다.
2. **이름 규칙에 생성기 단어가 들어갔다(#394, PR #446).** 서식 역할어 34개 중 11개가 생성기 틀에 있던 단어였다. 그 11개를 빼면
   이름 F1이 0.910 → 0.802로 내려갔다.
3. **기본 모델이 생성기 데이터로 학습했다(#458).** 그래서 합성 세트의 하이브리드 수치는 발표 숫자로 쓰지 않는다.
4. **실제로 재 보니 차이가 컸다(#456·#739).** 규칙을 고칠 때 본 문서 5종(조정용)에서 이름 재현율은 0.979인데,
   같은 다섯 종류를 틀과 이름부터 새로 쓴 보고용 세트에서는 0.567이다. 10/15~10/25 개선 기간에 조정용은 0.923 → 0.979로
   올랐지만 보고용은 그대로였다.

**그래서 어떻게 했나.** 데이터를 조정용과 보고용으로 나눴다(5번). 발표 숫자는 보고용과 외부 데이터(KDPII)로 낸다.

**예상 질문.**
- *그럼 0.987(합성 500건 전체 F1)은 의미가 없나?* → 같은 형식을 정확한 경계로 잡는지, 고친 것이 되돌아가지 않는지를
  보는 데는 맞다. 실제 문서에서의 성능을 말하는 숫자는 아니다.
- *왜 처음부터 보고용을 안 만들었나?* → 처음에는 세트가 하나였고, 규칙을 고치면서 그 세트를 봤다. #446에서 문제가
  드러나(#394 정비, PR #446) #456으로 나눴다. 나눈 뒤의 결과(조정용만 오름)가 이 문제를 숫자로 보여 준다.

**코드.** [`generator/entities.py`](../generator/entities.py) 23~24행 · [bench/README.md](../README.md) 「한계 고지」

## 5. 조정용과 보고용 나누기

**한 줄.** 규칙은 조정용 데이터의 미탐을 보고 고치고, 보고용은 집계 숫자만 본다.

**동작.**
- 지금 있는 세트(합성 500건 v1·v2, 표기 변형, 열린 미탐, 문서 5종 `doc_types_v1`)는 모두 조정용이다.
- 보고용은 새로 만든 `doc_types_holdout_v1`(200건, seed 456)과 외부 KDPII다.
- 보고용 세트는 조정용과 같은 다섯 종류(판결문·상담·메일·회의록·명단)지만 **문서 틀**과 **이름 음절**이 다르다.
  이름 음절은 학습 데이터와도 겹치지 않게 골라서, 모델이 외운 이름으로 점수를 얻지 못한다.
- 테스트가 세 가지를 확인한다. ① 이름 음절이 겹치지 않는다. ② 개인정보 자리를 지운 줄 틀이 판결문 양식 줄 말고는
  조정용과 겹치지 않는다. ③ 같은 시드로 바이트까지 재현된다.

**이렇게 만든 이유.** 머신러닝에서 시험 데이터를 보고 모델을 고치면 점수가 실력보다 높게 나오는 것과 같은 구조라서다.
보고용 미탐은 이슈·PR에 적지 않는다. 적는 순간 그 꼴에 맞춰 고치게 된다.

**다른 방법을 안 쓴 이유.** 기존 세트를 무작위로 반으로 나누는 방식: 같은 틀에서 나온 문장이라 반대쪽을 보고 고쳐도
그대로 맞는다. 틀 자체가 달라야 처음 보는 문서를 흉내 낼 수 있다.

**예상 질문.** *보고용도 같은 사람이 만들었으니 한계가 있지 않나?* → 맞다. 생성기를 모르는 사람이 틀을 쓰는 게
가장 좋다(#456 본문). 그래서 외부 데이터 KDPII를 함께 쓴다.

**코드.** [`generator/doc_types_holdout.py`](../generator/doc_types_holdout.py) · [`tests/test_doc_types_holdout.py`](../tests/test_doc_types_holdout.py)

## 6. 회귀 가드 — 고친 미탐이 다시 새지 않게

**한 줄.** core 이슈마다 그 미탐 꼴을 만드는 생성 함수를 두고, 고쳐진 이슈는 CI에서 계속 확인한다.

**동작.**
- 열린 미탐 세트(`open_misses_v1`)는 이슈 번호마다 태그를 단 문장을 만든다. 이슈별 재현율이 core가 고칠 때마다 오른다.
- 고쳐진 이슈 번호는 `FIXED_ISSUES`에 넣는다. 테스트가 그 태그마다 문장 30개를 새로 만들어, 지금 core가 전부 완전 일치로
  잡는지 본다. core가 되돌아가면 CI가 실패한다.
- 넣기 전에 생성기로 1,000건씩 만들어 흔들리지 않는지 본다. 예를 들어 #637은 1,000건 중 약 3%가 전화번호 종류로 잡혀서
  (가리긴 함) 넣지 않았다.

**이렇게 만든 이유.** 이름 규칙은 고치면 다른 꼴이 깨지기 쉽다. #600이 그랬다. 약한 단서 오탐을 고친 PR #571 뒤로
"담당자는 ○○○예요" 같은 문장 20건이 전부 새기 시작했는데, 합성 500건에는 이 어미가 없어 점수에 보이지 않았다.

**다른 방법을 안 쓴 이유.** 아직 안 고친 이슈까지 테스트에 넣으면 core가 미탐을 고칠 때마다 bench 테스트가 깨진다.
고친 것만 가드로 건다.

**코드.** [`generator/open_misses.py`](../generator/open_misses.py) `FIXED_ISSUES` · [`tests/test_open_misses.py`](../tests/test_open_misses.py)

## 7. 외부 데이터 KDPII로 다른 도구와 비교

**한 줄.** 학습에 쓰지 않은 한국어 대화 데이터(KDPII test 4,891문장)에서 maskingtape·ko-pii·Presidio를 같은 채점기로 잰다.

**동작.**
- `fetch_kdpii.py`가 Zenodo에서 받은 파일의 크기와 MD5를 확인하고, 우리 11종에 맞는 라벨 770개만 정답으로 쓴다.
  원자료와 변환본은 저장소에 싣지 않는다(CC-BY-4.0, git이 무시하는 폴더).
- **다 가림:** 정답 글자가 종류와 상관없이 모두 덮였는가(유출 관점). 번호는 숫자만 다 덮이면 가린 것으로 본다.
- **엉뚱한 곳 가림:** 정답과도, 직장·직위 같은 범위 밖 라벨과도 안 겹치는 탐지 수.
- 도구마다 경계를 자르는 관행이 달라 overlap F1을 주로 본다.

**결과(규칙 전용).** 다 가림 444/770(0.577), 엉뚱한 곳 17/460. ko-pii 전체 모드는 443/770, 엉뚱한 곳 274/1,243이다.
다 가린 수는 비슷하고, 엉뚱한 곳을 가린 수가 크게 적다.

**이렇게 만든 이유.** 합성 데이터는 우리 형식을 공유해서 다른 도구와 견주기에 우리 쪽에 유리하다(4번). 외부 데이터여야 공정하다.

**다른 방법을 안 쓴 이유.** 상대 도구의 라벨을 우리 기준으로 엄격하게 옮기지 않고 상대에게 유리하게 잡았다
(Presidio `LOCATION` → 주소 등). 비교에서 우리 쪽을 부풀리지 않으려고다.

**예상 질문.** *KDPII는 규칙 조정에 한 번도 안 썼나?* → 한 번 봤다. #601(PR #743)에서 KDPII에 새로 나온 오탐 낱말을 보고
거르기 목록에 넣은 적이 있고, README에 그대로 적었다.

**코드.** [`fetch_kdpii.py`](../fetch_kdpii.py) · [`evaluators/compare_kdpii_tools.py`](../evaluators/compare_kdpii_tools.py) ·
[`evaluators/pii_tool_adapters.py`](../evaluators/pii_tool_adapters.py)

## 8. 하이브리드(규칙 + 로컬 AI) 측정

**한 줄.** 같은 데이터를 규칙 전용과 하이브리드로 각각 돌려 나란히 비교한다. 하이브리드는 여러 번 돌려 범위로 적는다.

**동작.**
- 하이브리드는 core `llm_detectors()`다. 로컬 Ollama의 기본 모델(`maskingtape-name-1.5b`)이 이름을 찾고,
  규칙 탐지 결과를 전부 합친다. 그래서 규칙이 나아지면 하이브리드도 같이 오른다.
- 온도 0이어도 결과가 한두 건 흔들릴 수 있어서 2~5회 돌려 최소~최대를 적는다. 지금까지 흔들림은 재현율 0.002 이하였다.
- `compare_modes.py`는 문서마다 core를 한 번만 부르고(캐시) 이름·전체 지표와 문서당 시간을 함께 낸다.

**결과(보고용).** 문서 5종 이름 재현율 0.567 → 0.971~0.973, KDPII 이름 0.299 → 0.819. 대가는 오탐이다
(KDPII 이름 precision 0.964 → 0.465).

**예상 질문.**
- *오탐이 그렇게 늘어도 괜찮나?* → 내보내기 전에 한 번 더 거르는 도구라서 덜 가리는 것(유출)보다 더 가리는 쪽이 안전하다.
  F2가 이 판단을 숫자로 보여 준다.
- *KDPII 하이브리드가 예전 0.825에서 0.819로 내려간 이유는?* → 코드가 아니라 측정 환경 차이다. 0.825를 잰 10/4 커밋을
  같은 PC에서 돌려도 0.819가 나온다(이름 한 개 차이).
